# Pipeline Dedup & Discovery System

## Overview

This skill ensures every lead across all three MIFECO pipelines (Books, Consulting, SaaS) is unique. It maintains a **Master Lead Registry** (`leads-registry.json`) and provides a **dedup check tool** (`dedup-check.py`) that prevents duplicate leads from being processed across pipeline runs.

## When to Use

- **Before adding any new lead** to any pipeline — always run the dedup check
- **At the start of every pipeline orchestrator run** — Step 0: dedup discovery check
- **When enriching leads** — check registry to avoid registering duplicates
- **When cleaning up pipelines** — cross-reference leads against the registry

## Dedup Check — How to Use

### Batch Check (for multiple new leads)
Pipe a JSON array of lead objects to stdin:
```bash

```

Input format:
```json

  {"name": "Jane Doe", "company": "Acme Corp", "contact_email": "jane@acme.com"},
  ...
]
```

Response:
```json
{"results": [...], "duplicates_found": 1}
```

## Dedup Logic (3-Layer)

1. **Exact key match** — `lead_key = "name|org|email"` (fully normalized, lowercased, trimmed)
2. **Email match** — Same email address = same person = duplicate regardless of org
3. **Email domain + name match** — Same domain AND same person name = duplicate (catches same person using different org names, e.g. "Hope Fellowship" vs "Hope Fellowship Community Center")
4. **Same domain, different person** — NOT a duplicate. **Multiple contacts from the same organization are allowed.** This is intentional — you can message a CEO, a VP, and a team lead from the same company without them being flagged as duplicates.

## Registry Format Compatibility

The registry uses an **aggregate format** (pipeline-level IDs only, no lead detail fields):

```json
{
  "pipelines": {
    "books": { "leads": ["lead-001", "lead-004", ...] },
    "saas": { "leads": ["lead-003", ...] }
  },
  "total_leads_all": 18
}
```

The dedup script automatically detects this format and sources actual lead data (name, org, email) from `unified-pipeline.json` (or individual pipeline JSONs as fallback). It also supports the legacy **individual format** (flat list of dicts with `lead_key`/`name`/`email`/`organization` fields).

Field name normalization across pipelines:

| Pipeline | Name Field | Org Field | Email Field |
|----------|-----------|-----------|-------------|
| **SaaS** | `name` | `company` | `email` |
| **Books** | `contact.name` | `contact.organization` | `contact.email` |
| **Consulting** | `contact_name` | `company_name` | `contact_email` |
| **Unified** | `enrichment.contact_name` | `enrichment.company_name` | `enrichment.email` |

## Pitfalls

| Pitfall | Why It Happens | How to Avoid |
|---------|---------------|--------------|
| **Registry uses aggregate format** | `leads-registry.json` only stores pipeline-level IDs | Fix already applied: `dedup-check.py` auto-detects and builds dedup index from `unified-pipeline.json` |
| **Per-pipeline `leads` arrays are POC SAMPLES, not exhaustive** | Registry shows books: 5 IDs, consulting: 4, saas: 4 — but actual lead counts are 3, 10, 5. These arrays appear to be proof-of-concept examples, not comprehensive lists. | NEVER use `len(registry['pipelines'][p]['leads'])` for count verification. Use `registry['pipelines'][p]['total_leads']` and `registry['total_leads_all']` as the authoritative counts. |
| **Unified pipeline is a subset** | `unified-pipeline.json` may only contain 10 of 18 total leads — it's a separate convenience view, not a full reflection of all pipeline data. | Cross-reference unified IDs against per-pipeline lead IDs. Don't assume unified contains everything. |
| **Enrichment engine processes 1 lead per pipeline** | `python3 enrichment-engine.py --report` only examines ONE lead per pipeline file (stale check), not all leads. | Use the enrichment engine signal for stale-detection only. For full enrichment status, read each pipeline JSON directly and check all leads' `enriched_at` / `verification_status` fields. |
| **Case sensitivity** | "Acme Corp" vs "acme corp" | Lead_key normalizes to lowercase |
| **Whitespace** | " John " vs "John" | Script trims all values |
| **Same org, different person** | Both at HealthBridge Tech | Fixed: only blocks same email OR same name+domain |
| **Empty contact fields** | Consulting leads have no names/emails yet | Registry stores what exists — flagged for enrichment |
| **Old leads not in registry** | Leads added before registry existed | Pipeline orchestrator re-indexes them on first run |

#### Dedup Check Script

Create a CLI tool at `pipeline-engine/data/dedup-check.py` that checks three layers:

```
Layer 1 — Exact match: lead_key (name|org|email) must match exactly → DUPLICATE
Layer 2 — Email match: same email address → DUPLICATE (same person)
Layer 3 — Email domain + name: same email domain AND same contact name → DUPLICATE
         Same company, different person → ALLOW (NOT a duplicate)
```

**Script design:**

```python
#!/usr/bin/env python3
import json, sys, os

REGISTRY_PATH = os.path.join(os.path.dirname(__file__), "leads-registry.json")

def load_registry():
    if os.path.exists(REGISTRY_PATH):
        with open(REGISTRY_PATH) as f:
            return json.load(f)
    return {"leads": []}

def make_key(name, org, email):
    n = (name or "").strip().lower()
    o = (org or "").strip().lower()
    e = (email or "").strip().lower()
    return f"{n}|{o}|{e}"

def check_duplicate(name, org, email):
    key = make_key(name, org, email)
    registry = load_registry()
    for lead in registry["leads"]:
        # L1: Exact key match
        if lead["lead_key"] == key:
            return True, lead
        # L2: Same email
        if email and lead.get("email","").lower() == email.lower():
            return True, lead
        # L3: Same domain + same name
        if email and lead.get("email",""):
            d1 = email.split("@")[-1].lower() if "@" in email else ""
            d2 = lead["email"].split("@")[-1].lower() if "@" in lead.get("email","") else ""
            n1 = (name or "").strip().lower()
            n2 = (lead.get("name","") or "").strip().lower()
            if d1 and d1 == d2 and len(d1) > 3 and n1 and n1 == n2:
                return True, lead
    return False, None
```

#### Verification Checklist

For each lead, run through this checklist in order (stop at the first strong signal):

| # | Check | Method | What To Look For | Verdict If Failed |
|---|-------|--------|-----------------|-------------------|
| 1 | **Organization website** | Navigate to the organization's claimed URL | Active, real business website with matching description | ⚠️ Flag — dead/parked domain or wrong business |
| 2 | **Email domain** | Check if the domain resolves (browser_navigate or `dig`) | Domain actually serves web content | ⚠️ Flag — unrouteable domain (.edu that doesn't resolve, etc.) |
| 3 | **Google Maps** | Search for the organization name + city | Real physical location or identifiable business | ⚠️ No physical presence found |
| 4 | **Staff/leadership roster** | Navigate to About/Team/Staff/Faculty page | The contact person actually works there | ⚠️ Not on current roster (may be former staff) |
| 5 | **Social media presence** | Check Facebook, LinkedIn, Instagram, etc. | Active, legitimate social media accounts | Minor concern — absence is not disqualifying |
| 6 | **Referral source verification** | Search for the claimed referral source (e.g., "BookExpo 2026") | The event/source actually exists | Minor concern — doesn't validate the lead directly |
| 7 | **Domain registrar status** | For suspicious domains, check if the domain is for sale | The domain is actively used by the business, not parked/listed for sale | 🔴 Major red flag — domain-for-sale = likely dead lead |
| 8 | **Email format validation** | Check if known addresses from the same org follow a consistent pattern | The lead's email follows the org's observed format (e.g., `firstname@org.edu` vs `first.last@org.org`) | ⚠️ Mismatch doesn't disprove the lead but warrants caution |

**Execution pattern:** Use `delegate_task` in parallel (up to 3 at once via `max_concurrent_children`) to research multiple leads simultaneously. Each subagent gets one lead with its specific verification goals.

#### Verification Status Grading

Assign each lead a verification status after research:

| Grade | Meaning | Follow-up Action |
|-------|---------|-----------------|
| ✅ **Confirmed** | Organization verified + contact confirmed on roster/website | Proceed with normal outreach |
| ✅ **Likely Real** | Organization verified, contact not found on roster but email domain matches org pattern | Send outreach — non-response is confirmation |
| ⚠️ **Needs Verification** | Organization exists but contact isn't on roster, email domain format is uncertain | Try alternate email format or call main line |
| ⚠️ **Suspicious** | Domain listed for sale, no physical presence, or inconsistent details | Send a test email — if it bounces, mark as dead |
| 🔴 **Dead** | Email bounces, organization doesn't exist, or all checks fail | Remove from active pipeline |

#### Batch Enrichment Results Update Pattern

After running enrichment on multiple leads (via delegate_task or sequential research), update the pipeline JSON programmatically with ALL enrichment fields, not just notes:

```python
#!/usr/bin/env python3
import json
from datetime import datetime, timezone

now = datetime.now(timezone.utc).strftime('%Y-%m-%dT%H:%M:%SZ')

enrichment = {
    'C-001': {
        'contact_name': 'Phillip Berry',
        'contact_email': 'pberry@company.com',
        'website': 'company.com',
        'phone': '(555) 123-4567',
        'notes': 'ENRICHED YYYY-MM-DD: Verified real company...',
        'verification_status': 'Confirmed',
        'icp_score': 5,        # 0-10 product fit
        'enriched_at': now,
        'enriched_by': 'agent-enrichment'
    },
    # ... one entry per lead
}

with open('data/pipeline-{product}.json') as f:
    data = json.load(f)

for lead in data['pipeline']['leads']:
    e = enrichment.get(lead['id'])
    if not e:
        continue
    # Update contact fields
    if e.get('contact_name'):
        lead['contact_name'] = e['contact_name']
    if e.get('contact_email'):
        lead['contact_email'] = e['contact_email']
    if e.get('website'):
        lead['website'] = e['website']
    if e.get('phone'):
        lead['phone'] = e['phone']
    # Update metadata
    lead['notes'] = e.get('notes', lead['notes'])
    lead['verification_status'] = e.get('verification_status', 'Unverified')
    lead['icp_score'] = e.get('icp_score', 0)
    lead['enriched_at'] = e.get('enriched_at', now)
    lead['enriched_by'] = e.get('enriched_by', 'agent')
    # Compute rank with hard-gate: no contact = rank 0
    v_lookup = {'Confirmed': 10, 'Likely Real': 7, 'Needs Verification': 3, 'Suspicious': 1, 'Dead': 0, 'Unverified': 1}
    v = v_lookup.get(lead.get('verification_status', 'Unverified'), 0)
    c = 10 if e.get('contact_name') and e.get('contact_email') else (5 if e.get('contact_name') or e.get('contact_email') else 0)
    f = e.get('icp_score', 0)
    # HARD GATE: no contact info = rank 0
    if not e.get('contact_name') or not e.get('contact_email'):
        lead['rank'] = 0
    else:
        lead['rank'] = v + c + f

data['pipeline']['summary']['enriched_leads'] = sum(1 for l in data['pipeline']['leads'] if l.get('enriched_at'))
data['pipeline']['summary']['last_enrichment_run'] = now

with open('data/pipeline-{product}.json', 'w') as f:
    json.dump(data, f, indent=2)
```

This pattern runs automatically after a batch enrichment session. For the `v_lookup` scoring: leads that don't exist on the web get `verification_status='Dead'` → `v=0` → they rank at most 5 (from product fit), pushing them into the 0-4 Dead/Synthetic range.

#### Dead Lead Detection During Enrichment

When researching a lead, if **no registered business entity exists** for the claimed organization name (no website, no business registration, no LinkedIn, no credible directory listing), classify it as **Dead** and remove from the active pipeline:

1. **Exhaustive search:** Run web searches for the exact name + "Inc", "LLC", "Corp", "NGO", "Nonprofit". Check business registries (OpenCorporates, Secretary of State sites), Guidestar for nonprofits, LinkedIn.
2. **Name variation search:** If exact name fails, search stripped-down versions (e.g., "Summit Nonprofit Alliance" → "Summit Nonprofit" → "Summit Alliance").
3. **Confirm dead:** After all searches return no registered entity, mark as `verification_status: "Dead"` and `rank: 0`. Set `status: "removed"` in the pipeline.
4. **Registry preservation:** Keep the lead in `leads-registry.json` with `status: "archived"` so a subsequent enrichment run doesn't re-discover and re-add the same fake lead.
5. **Report:** Log the dead lead in the enrichment report with the search queries used and results found, so a human can verify the decision.

#### Pitfalls

| Pitfall | Why It Happens | How to Avoid |
|---------|---------------|--------------|
| **Confusing "no web presence" with "not real"** | Small/local businesses may have minimal or no website | Check Google Maps + social media. A missing website is not disqualifying for a local business. |
| **Assuming faculty/staff pages are complete** | Schools and small orgs don't always list all staff | Absence from a roster page is suspicious but not definitive. Note it but don't kill the lead on this alone. |
| **Domain-for-sale = dead lead** | Domains can be parked by the owner who still uses the email | The `whois` data may show the same registrant as the claimed business. Test the email address directly. |
| **Treating all leads the same** | Using the same level of verification for a $50 lead as a $6,000 lead | Scale verification effort to deal size. High-value leads (top 20%) get full checklist; low-value leads get checks 1-3 only. |
| **Not updating the pipeline JSON** | Verification is done, notes are in-memory, but the pipeline file stays stale | Always update `notes` and `updated_at` in the pipeline JSON after enrichment so future orchestrator runs have context. |
| **All DuckDuckGo searches returning empty** | Rate limiting — roughly 8 sequential calls triggers empty results; subsequent DDGS instances in the same process also return empty | Use `delegate_task` to run searches in parallel — each subagent gets its own independent DDGS instance with a fresh rate limit. Each subagent should handle 3-5 queries max. If DDGS starts returning empty in the main agent, spawn subagents for remaining queries. Restarting the Python process also resets the rate limit. |
| **Enrichment engine `--report` only processes 1 lead per pipeline** | `enrichment-engine.py` examines only ONE lead per pipeline file (for stale detection), not all leads. Its `--report` says "1 leads" even when a pipeline has 10. | Use the enrichment engine for stale-detection signals only. For full enrichment status, read each pipeline JSON directly and check all leads' `enriched_at` / `verification_status` / `rank` fields. The orchestrator should enumerate `data['pipeline']['leads']` directly. |

### STEP 2.6: Lead Scoring & Ranking

After verification, score each lead across three dimensions and produce a ranked list across all pipelines. This determines outreach priority.

**Score Components:**

| Dimension | Max Score | What To Measure |
|-----------|-----------|-----------------|
| **Verification** | 10 | ✅ Confirmed=10, ⚠️ Verified partial=5, ❌ Unverified/Synthetic=0 |
| **Contact Availability** | 10 | Valid email+LinkedIn=10, Valid email only=8, Email may work=5, No contact found=0 |
| **Product/Consulting Fit** | 10 | Strong alignment=10, Moderate=5, Weak or unknown=0 |

**Total Score = Verification + Contact + Fit (max 30)**

**⚠️ HARD GATE: No Contact Info = Rank 0**
A lead with a **null/empty contact_name OR null/empty contact_email** has its TOTAL rank set to **0**, regardless of other dimensions. Reasoning: a lead you cannot reach is invisible to the pipeline. The lead must exist in the pipeline JSON (for tracking purposes) but ranks 0 until enriched. This overrides all other score components.

Implementation example:
```python
if not lead.get('contact_name') or not lead.get('contact_email'):
    lead['rank'] = 0
else:
    lead['rank'] = v_score + c_score + f_score
```

**Classification Thresholds:**
| Score | Classification | Action |
|-------|---------------|--------|
| 25+ | 🔥 Hot | Generate outreach (email + LinkedIn + media) immediately |
| 15-24 | Warm | Generate outreach but deprioritize vs hot leads |
| 5-14 | Cold | Send test email to verify before full outreach |
| 1-4 | Dead/Synthetic | Remove from active pipeline or flag for review |
| **0** | **No Contact Info** | **Enrich first — cannot rank/reach** |

**Synthetic Lead Detection:** If a company has no website, no domain that resolves, no Google Maps presence, and no social media — and especially if multiple leads share similar patterns (generic name + unrouteable domain + high ICP score) — flag them as **synthetic/fabricated**. Do NOT send outreach. **IMPORTANT:** When removing synthetic leads from a per-product pipeline JSON, also remove them from the unified pipeline (`unified-pipeline.json`) if one exists — it has its own `leads` array that must stay in sync. The unified pipeline uses prefixed IDs (e.g., `saas-002`), so match on company name or ID number.

### Nurture Sequence Content Audit & Maintenance

**Trigger:** When the daily pipeline orchestrator flags nurture sequence content discrepancies (wrong product names, wrong book titles, missing catalog items). The orchestrator detects these mismatches and puts email sends ON HOLD — this procedure tells you how to fix them.

**This is a separate workflow from creating sequences from scratch.** The sequences already exist; you're correcting content errors discovered during daily monitoring.

#### Common Discrepancy Patterns

| Pattern | Detection | Root Cause |
|---------|-----------|------------|
| **Wrong book titles** | Books nurture uses "Ignition" but pipeline catalog says "Built from Dust"| Nurture sequence was created before final titles were set |
| **Wrong product names** | SaaS nurture references "LaunchPad" but actual products are Project Hypatia Pro, PM Accelerator, VibraEngineer | Nurture sequence was a generic template, not customized for MIFECO |
| **Missing catalog items** | Pipeline catalog has 7 books, nurture only lists 5 (missing AI That Works for Small Business) | Catalog expanded after nurture was created |
| **Wrong pricing** | Nurture lists $11.99 for a title, pipeline catalog says $9.99 | Prices changed after initial setup |
| **Article prefix variance** | Pipeline says "Oxygen Gamble" but nurture says "The Oxygen Gamble" (same for "Red Charter"/"The Red Charter") | Pipeline uses short/slug titles; nurture uses full display titles with "The" prefix. Decide which is canonical and align both. |

#### Fix Procedure

**1. Load pipeline catalog and nurture sequence side-by-side.**
Read the pipeline JSON data file first (`pipeline-{product}.json` — specifically the `books_available` or key catalog section) and the nurture sequence file (`sequences/{product}-nurture.json`). Compare their data sections for mismatches.

**2. Fix the nurture sequence `books_available` (or product listing) section first.**
Update volume titles, product names, prices, and add missing entries to match the pipeline catalog exactly:

```json
// BEFORE — wrong
{"volume": 1, "title": "No Blue Sky: Ignition", "price": 9.99}

// AFTER — correct
{"volume": 1, "title": "No Blue Sky: Built from Dust", "price": 9.99}
```

**3. Fix ALL email body references.**
For each email in the sequence, search for every occurrence of the old name/title in the `body` field. This includes:
- Catalog/summary sections listing prices or volumes
- Bulk discount examples (e.g., "A Classroom Set of No Blue Sky: Ignition")
- Reader reviews or testimonials that mention specific titles
- Subject lines that reference specific products

Use `patch(mode="replace", path=..., old_string=..., new_string=...)` for each unique string. When the `body` field contains JSON-escaped newlines (`\n`), patch can double-escape them — prefer writing the entire file fresh instead.

**4. Validate JSON integrity.**
```bash
python3 -c "import json; json.load(open('sequences/{product}-nurture.json')); print('✅ Valid')"
```

**5. Verify all copies of wrong names are gone.**
Search the fixed file for the old strings to confirm zero remaining references:
```bash
grep -i "oldtitle\|wrongname" sequences/{product}-nurture.json
# Should return nothing
```

**6. When the fix is complete, the orchestrator's next run will move the held emails from "⏸️ ON HOLD" to "✅ Ready to send".** No manual re-run needed.

#### Full Rebuild vs. Patch

| Scenario | Approach | Example |
|----------|----------|---------|
| Minor title/name changes | Patch individual strings | Books nurture: Ignition→Built from Dust, Ascent→The Oxygen Gamble |
| Complete product mismatch | Full rebuild | SaaS nurture: Entire sequence references a non-existent product "LaunchPad" — every email is wrong |
| Partial mismatch + missing items | Patch + add | Books nurture had wrong titles AND missing AI That Works for Small Business |

**Full rebuild pattern:** When the nurture sequence was built from a generic template for a completely different product line (e.g., "LaunchPad" was a coaching/course platform, but actual MIFECO products are project management tools), the fastest approach is to **write a completely new file** rather than patching individual strings. - Day 1: Suite overview + product matching ("which one fits you?")
- Day 2-4: Deep-dive each product individually
- Day 5: Case studies/real workflows
- Day 6: Transparent pricing
- Day 7: Path-forward options (trial, demo, stay informed)

#### Pitfalls

| Pitfall | Why It Happens | How to Avoid |
|---------|---------------|--------------|
| **Only fixing the catalog section, missing email bodies** | The `books_available` section at the top is obvious; embedded title references in email `body` fields are hidden in long JSON strings | Search every email's `body` for all old title strings. A common miss is the bulk discount example in the final email. |
| **Double-escaped JSON from patch** | The patch tool re-escapes text that already contains escaped newlines (`\n`), producing `\\n` in the JSON string | When a file has JSON with embedded `\n` (newline escape sequences), write the entire file fresh instead of patching individual strings within body fields |
| **Existing double-escaped newlines (`\\\\n`) in historical files** | Previous patch operations or manual edits produced `\\\\n` (literal backslash-backslash-n) instead of `\n` (newline). If found, the file needs a full rewrite or a global `\\\\n` → `\n` fix. Validate by running `python3 -c "import json; d=json.load(open('file.json')); body=d['email_sequences'][-1]['body']; print(body.count('\\\\n'))"` — should be 0 for well-formed files. |
| **Forgetting to add missing products** | Only the titles that changed get attention; products added since the nurture was created go unnoticed | Always compare the nurture's `books_available` against the pipeline catalog's `books_available` — add any that are missing |

#### STEP 6.1: What the Daily Cron Does

The daily pipeline orchestrator cron job performs the following operations in order:

4. If a lead appears in a pipeline JSON but is NOT in the registry, re-register it
5. Verify registry lead count matches total leads across all pipeline files

**STEP 1: Read All Pipeline Data**
- Read each pipeline JSON: `pipeline-saas.json`, `pipeline-consulting.json`, `pipeline-books.json`

- Read the master lead registry: `leads-registry.json`
- Read any unified pipeline: `unified-pipeline.json`

**STEP 2: Calculate Days-in-Stage (per pipeline)**

For each lead, determine when they entered their CURRENT stage:

```python
def stage_entry_time(lead, stage_num):
    # 1. Check stage_history for an entry matching current stage
    for entry in lead.get('stage_history', []):
        if entry.get('stage_id') == stage_num:
            return entry.get('entered_at')
    # 2. If not found, use exit time of PREVIOUS stage
    prev_stage = stage_num - 1
    for entry in lead.get('stage_history', []):
        if entry.get('stage_id') == prev_stage:
            return entry.get('exited_at')
    # 3. Fallback to created_at
    return lead.get('created_at')
```

**Critical:** Do NOT fall through to `created_at` for leads that have a stage_history with previous stage exits — the exit of the previous stage IS the entry of the current stage. Using `created_at` overestimates days-in-stage.

**⚠️ Timezone pitfall:** Pipeline data may mix tz-aware dates (`"2026-04-28T00:00:00Z"`) with tz-naive date-only fields (`"created_date": "2026-04-20"`). When comparing against `datetime.now(timezone.utc)`, Python raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. Always normalize: parse to offset-aware if Z/offset present, otherwise treat as UTC-relative:

```python
from datetime import datetime, timezone
def parse_date(s):
    dt = datetime.fromisoformat(s.replace("Z", "+00:00"))
    if dt.tzinfo is None:
        dt = dt.replace(tzinfo=timezone.utc)
    return dt
```

### STEP 10.3: Email Enrichment Gate — Block Unsafe Sends

**Trigger conditions:** Use this procedure when the content command center has nurture sequence emails with template placeholders (`{{email}}`, `{{name}}`) instead of real recipient addresses, and you need to prevent them from appearing as sendable.

**Class:** "Enforcing email validation gate in content command center dashboards — no email without a real `to:` address should reach the sendable viewer."

#### The Problem

Nurture sequence emails are templates — they use `{{email}}`, `{{name}}`, `{{company}}` placeholders. If these appear in the EMAILS viewer alongside emails with real `to:` addresses (e.g., `alice@testcorp.com`), a user could accidentally try to send a template without lead data and get a bounced/silently-failed email.

#### The Fix Pattern

1. **Split EMAILS into two arrays:**
   - `EMAILS` — only items with valid `to:` addresses (real emails like `user@domain.com`)
   - `EMAIL_TEMPLATES` — items with placeholder `to:` fields, marked as `NEEDS_ENRICHMENT`

2. **Add a separate Enrichment viewer tab** that displays templates needing enrichment:
   - Shows the `NEEDS_ENRICHMENT` badge prominently
   - Warns the user that pairing with a lead is required before sending
   - Filters by pipeline and text search

3. **Add client-side email validation** before sending:
   - `isValidEmail()` — regex check for valid email format
   - `getEmailFromToField()` — extract email from `"Name <email>"` or bare `"email"` format
   - In `sendEmailForReal()`, validate the `to:` field and block with an alert if no real email found

4. **Template state model:**
   ```javascript
   // EMAIL_TEMPLATES — each has to: 'NEEDS_ENRICHMENT'
   {id:'em1',pipeline:'SaaS',day:1,from:'Sender <sender@domain.com>',to:'NEEDS_ENRICHMENT',subject:'Welcome {{name}}',body:'Hi {{name}}...',cta:'Reply'}
   
   // After enrichment — moved to EMAILS with real address
   {id:'em1',pipeline:'SaaS',day:1,from:'Sender <sender@domain.com>',to:'John Doe <john@company.com>',subject:'Welcome John!',body:'Hi John...',cta:'Reply'}
   ```

5. **Render difference:** The `renderEmails()` function only displays items from `EMAILS`. Templates in `EMAIL_TEMPLATES` go to a separate `renderEnrichmentQueue()` function.

6. **Enrichment workflow:**
   - Look up matching leads from pipeline JSON data that have `contact_email` fields
   - Replace `{{name}}` and `{{email}}` with actual lead data
   - Update `to:` from `NEEDS_ENRICHMENT` to the real recipient
   - Move the enriched item from `EMAIL_TEMPLATES` to `EMAILS`
